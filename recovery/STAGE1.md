# Этап 1: восстановление старой сборки

Завершён 20 октября 2026 года. Базовый коммит: `80f0c44d2c6541ea43a4fdc9ff3598fa9e9e01fc`,
ветка `recovery/initial-audit`. Изменения находятся в рабочем дереве, без коммита и отправки.

Полный reactor из 9 модулей проходит `clean package` на Windows 11 x64,
Temurin 8u504-b01 и Maven 3.3.9. Выполнены 7 JUnit-тестов, ошибок/провалов/пропусков нет.
Получен `assembly/target/raox-3.9.0.zip`. Jenkins и внешний Eclipse для сборки не нужны.
Проверка повторена на новой копии исходников с существующим Maven/p2-кэшем.

## Команда

Подготовка переносимых инструментов и структура каталогов описаны в
[build-with-maven.md](../build-with-maven.md); ссылки и хеши — в
[toolchains.json](evidence/toolchains.json).

Из корня проекта:

```powershell
.\recovery\Invoke-LegacyBuild.ps1 -ToolchainRoot C:\raox-tools -CacheRoot C:\raox-m2 -Clean
```

Проверенная команда на текущем компьютере:

```powershell
$raoxWork = 'C:\Users\propinbo\Documents\Codex\2026-10-20\https-www-google-com-url-q\work'
.\recovery\Invoke-LegacyBuild.ps1 `
    -ToolchainRoot (Join-Path $raoxWork 'toolchains') `
    -CacheRoot (Join-Path $raoxWork 'm2') -Goal package -Clean
```

`-RepoRoot` позволяет указать другую копию исходников; `-LogRoot` — каталог свидетельств.
Скрипт сохраняет версию Maven/JDK, полный лог, код завершения, сумму результатов JUnit,
состав и SHA-256 архива. `succeeded` учитывает и Maven, и последующую проверку артефакта.
Окружение вызывающего PowerShell восстанавливается в `finally`.

## Исправленные препятствия

1. В `exec-maven-plugin` открытый диапазон EMF из Xtext parent выбирал современные
   библиотеки, включая Equinox common 3.21.0 для Java 17. Зафиксированы Maven-зависимости
   генератора: EMF common 2.11.0, ecore/xmi 2.11.1, codegen/codegen.ecore 2.11.0,
   Equinox common 3.6.0, ANTLR runtime 3.2 и xtext-antlr-generator 2.1.1
   (его транзитивный `org.xtext:antlr-generator` — 3.2.1).
   Удалено дублирование Equinox под двумя Maven artifactId.
2. Генерация прошла, но Xtend упал с `SecurityException` о несовпадающих подписях классов
   `org.eclipse.core.runtime`: его собственный Maven-classpath тоже получал современный
   EMF codegen и Eclipse platform. Для Xtend отдельно зафиксированы common, ecore, xmi и
   codegen. После этого скомпилированы язык, UI и тесты.
3. В обоих ANTLR fragments задано `-Xconversiontimeout 0`. В используемом генераторе
   `DFA.MAX_TIME_PER_DFA_CREATION` по умолчанию равен 1000 мс; нулевое значение отключает
   преждевременное завершение анализа. Грамматика `.xtext`, JDK/Xtext/Tycho и математические
   библиотеки не обновлялись.
4. В дескрипторе копии runtime путь `/` заменён на `./`: устранено сообщение упаковщика
   `[ERROR] OS=Windows ... *nix-specific root-relative-reference`.
5. Добавлены автоматическая проверка состава ZIP и совпадения runtime, параметр `-Clean`,
   запись окружения/результатов, проверка JDK 8 и понятная ошибка для неподдерживаемого
   пути к исходникам. Обновлены README и инструкция сборки.

## Windows-пути и Unicode

Проверены исходные параметры `file://${project.basedir}/...` и
`runtimeProject=/${project.basedir}`: они работают в текущем ASCII-пути и в новой копии
`stage1-ascii\clean sources` с пробелом. Их изменение не потребовалось.

Отдельная чистая копия `stage1-clean\исходники с пробелами` выявила другой дефект:
ANTLR 3.2.1 падает при чтении внутренней `InternalRao__.g` с `unexpected char: '\'`,
после чего Xtext не находит сгенерированный lexer. Изолированный запуск того же
ANTLR из Java воспроизводит ошибку без Maven; во внутренней грамматике присутствуют
директивы `// $ANTLR src` с Unicode-путём. Исправление старого ANTLR в этот этап не включено.
**Исходники нужно размещать в ASCII-пути**; скрипт проверяет это до запуска сборки.
Модели при этом могут использовать кириллицу и другие Unicode-идентификаторы.

Предупреждение старого README о `RULE_ANY_OTHER` проверено на неизменённой грамматике.
Точное сообщение на этой машине при стандартных настройках не возникло, поэтому
приписывать ему доказанную причину нельзя. Контролируемый запуск с лимитом 1 мс
воспроизводит ошибки анализа parser/lexer, а тот же запуск с лимитом 0 проходит:
[ошибка](evidence/antlr-timeout-1ms.log), [успех, пустой stderr/stdout](evidence/antlr-timeout-disabled.log),
[параметры и коды](evidence/antlr-probes.json).
Отключение таймера и автоматические Unicode-проверки заменяют совет о случайных повторных запусках.

`UnicodeIdentifierTest` проверяет оба generated lexer на `Имя_ресурса42`, `Δοκιμή`, `模型`,
`café`, комбинируемый знак, escaped keyword и Unicode escape. Дополнительно проверяются
`RULE_ANY_OTHER` для `@` и сохранение имён парсером при чтении `constant <имя> = 1`.

## Артефакт и границы результата

В рабочем каталоге: `assembly/target/raox-3.9.0.zip`,
SHA-256 `8f22d14671c38a142d04c483ac5891d3907655d7102f9b6d97248ccbe28b5572`.
[Состав и хеши](evidence/stage1-workspace-package.json).

В ZIP ровно пять файлов внутри `raox/`: язык, runtime, UI, game5 и runtime без версии.
Две копии runtime имеют одинаковый SHA-256. SDK feature собирается отдельно,
как предусмотрено исходной конфигурацией. Это архив плагинов, без установленного Eclipse.
Компоненты reactor не исключались, тесты не подавлялись.

Хеши разных сборок отличаются: старый упаковщик сохраняет время файлов, а генерация
может включать путь к исходникам. Побитовая воспроизводимость не установлена.
Остаются предупреждения метаданных исчезнувших Codehaus-репозиториев, конфигурации
старых fragments и вспомогательных assembly-артефактов; они не мешают показанным сборкам.
Фиксация полной p2-платформы, проверка пустого кэша, HTTPS/зеркало и CI относятся к этапу 3.
Установка и запуск готового дистрибутива проверяются отдельно по roadmap.
