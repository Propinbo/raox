## Разбор старых тестов

`LinearProcessTest` задаёт интервал генерации 10 и обслуживание 15 без очереди.
Один транзакт может ждать в выходном хранилище Generate. При `t=50` следующему
транзакту уже некуда попасть, Seize занят, а сканер получает `CHECK_AGAIN` без
успешного продвижения. Возвращается `RUNTIME_ERROR`. Это проверка перегрузки
данной схемы, а не требование падать для любого линейного процесса.

Допуск `abs(time - 40) < 1e16` заменён точным ожиданием `50.0`; целочисленные
времена представляются без округления. Добавлена успешная схема с интервалом 20:
нормальная остановка при `60.0`. Очередь завершает исходный сценарий при `70.0`.
Ветвление заменено на явное чередование двух ветвей, остановка при `65.0`.
Конструктор `SelectPath(probability)` создаёт генератор без доступного seed,
поэтому его случайный выбор не используется как воспроизводимый тестовый оракул.
Изменений runtime для маскировки перегрузки не потребовалось.

## Порядок и численные правила

- Seed исторических случайных моделей — `123456789`, параметры взяты из исходных
  шаблонов. Генераторы строк и списки детерминированы без случайного seed.
- Текст трасс и результатов сравнивается точно после нормализации CRLF/LF.
  Численные допуски для эталонов отсутствуют: это контроль прежнего JDK/runtime,
  а не разрешение менять математику при переносе платформы.
- Отдельный тест Uniform проверяет 100 000 значений в `[0,1)`, среднее `0.5 ± 0.005`
  и дисперсию `1/12 ± 0.002`. Эта проверка не зависит от эталонного текста.
  Статистические свойства остальных распределений этим тестом не доказаны.
- Планировщик выдаёт разные моменты в возрастающем порядке. Для одинакового
  времени старый `PriorityQueue` не обещает FIFO: проверяется, что все события
  сохранены и выданы по одному. Случайный порядок кучи не объявлен нормой языка;
  переход к FIFO потребует отдельного решения с проверкой совместимости.
- Результаты и decision points теперь инициализируются в порядке объявлений `.rao`,
  а не в неопределённом порядке `Class.getDeclaredFields/Classes`. Есть модель с
  конфликтующими правилами и обратными алфавитными именами для проверки этого порядка.

## Исправления, необходимые для проверки

1. `ModelInternalsParser.postprocessModel()` выделяет обработку скомпилированной
   модели без обращения к workspace; UI продолжает подключать `.proc` в `postprocess()`.
2. Текстовый `ResultsParser.parseAsString()` больше не обращается к `Display.getCurrent()`.
   Формат текста сохранён, стили для UI по-прежнему формируются при обновлении представления.
3. На Windows/SWT обнаружена рекурсивная перерисовка таблицы трассы:
   `PaintListener → TableColumn.pack → WM_PAINT → PaintListener`.
   В релизе 3.9.0 этого обработчика нет: он добавлен последним изменением текущей ветки.
   `pack()` перенесён в обновление данных. Дамп зависшего AUT сохранён в
   [stage2-trace-paint-recursion.txt](evidence/stage2-trace-paint-recursion.txt).
4. В RCPTT обновлены селекторы для Oxygen: `Open` вместо `OK`; мастер
   `Rao X/Rao X Project` выбирается явно. Фильтр `rao` прежде выбирал game5.
5. В мастере game5 валидация имени переведена с `KeyListener` на `ModifyListener`:
   вставка текста и программное заполнение теперь включают Finish так же, как ввод с клавиатуры.
6. UI-прогон выявил `ConcurrentModificationException` в `RealTimeUpdater`: таймер
   обходил `HashSet` одновременно со снятием подписок при остановке симуляции.
   Применён `CopyOnWriteArraySet`, флаги видимости данных и паузы сделаны `volatile`.
   [Исходный стек](evidence/stage2-timer-race.txt).
7. Запуск без ожидания UI-job выявил `ClassNotFoundException`: Run полагался на
   асинхронную автосборку, которая ещё не создала `.class`. Теперь Run, как и Build,
   дожидается сборки проекта; после генерации выполняется синхронный incremental pass
   для Java-файлов, созданных Xtext. [Исходный стек](evidence/stage2-run-before-compile.txt).

## Проверка релиза и интерфейса

Для UI используется переносимый Windows x64-дистрибутив релиза 3.9.0 и RCPTT 2.2.0,
без системной установки. Runner выполняет UI-сценарии, создаёт отдельный workspace
и HTML/JUnit-отчёты. Важно явно инъецировать четыре versioned Rao bundle:
RCPTT не подхватывает `dropins` исходного AUT автоматически. Копия runtime без версии
не инъецируется вторым bundle с тем же symbolic name.

У UI отдельная историческая платформа Oxygen с Xtext/Xbase **2.12.0**;
Maven-сборка и JUnit по-прежнему используют Xtext **2.9.2**. Эти окружения нельзя
называть одной зафиксированной target platform. Согласование и фиксация платформы
остаются задачей этапа 3; оба проверенных окружения указаны явно.

На оригинальных бинарниках релиза успешно прошли четыре сценария: пустая модель,
`uniform_sequence` с точным сравнением исторической трассы, тот же запуск без
трассировки и открытие перспективы Rao. Это реальное выполнение опубликованных JAR.

Команда для собранных плагинов:

```powershell
.\recovery\Invoke-RcpttTests.ps1 `
  -JavaHome C:\raox-tools\jdk8u504-b01 `
  -RunnerRoot C:\rcptt-2.2.0\eclipse `
  -AutRoot C:\raox-eclipse-3.9.0-win-x64 `
```

`-Tests '*ui_*'` ограничивает прогон новыми проверками. Без фильтра запускаются

## Ограничения, не являющиеся требованиями совместимости

У событий с равным временем нет гарантированного FIFO. У вероятностного SelectPath
нет API для seed. Параметр `Normal`, названный `variance`, в реализации умножается
как масштаб (стандартное отклонение); исправление его смысла без отдельной численной
проверки изменило бы старые модели. Эти вопросы не скрыты заменой эталонов.

Проверки используют прежние версии JDK/математических библиотек. Пустой кэш,
другая машина, полная фиксация p2 и CI относятся к этапу 3. Новый готовый дистрибутив
в этом этапе не создаётся: UI выполняется на историческом Eclipse с текущими плагинами.
